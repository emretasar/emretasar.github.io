## Special Member Functions
Special member functions are the functions that the compiler might generate for us. They provide fundamental functionality of a class such as copy, move, initialization and clean up functionalities.

```cpp
class Widget 
{
	Widget();                         // Default Constructor
	Widget(Widget const&);            // Copy Constructor
	Widget& operator=(Widget const&); // Copy Assignment Operator
	Widget(Widget&&) noexcept;        // Move Constructor
	Widget& operator=(Widget&&);      // Move Assignment Operator
	~Widget();                        // Destructor
}
```

### 1- The Default Constructor
- Compiler generate this constructor if there is no other constructor in your class. Ih there are any other constructor in your class, this one is not generated by the compiler. 
- Also all data members and base classes must be default constructed to be able to generate default constructor by the compiler. If any data member without default constructor exists in the class, compiler can not generate default constructor of this class.
- The compiler generated default constructor initializes all data members of class(user-fefined) type. But it does not initializes the data members of fundamental type. For example, you have int, string and a pointer in your class, default constructor initializes string with empty string but int and pointer are not initialized by the compiler generated default constructor. To avoid this uninitialization problem, programmer should prefer value initialization instead of default initialization.
```cpp
struct Widget {
	int i;
	std::string s;
	int* pi;
};

int main() {
	Widget w1;   // Default initialization - only initialize string
	Widget w2{}; // Value initialization - all initialized as 0,'',nullptr
}
```
In value initialization, all members are zero initialized first then default constructor is called. So, we able to avoid uninitialization problem. This is one of the reasons why the value initialization should be our first prefer.  

If the programmer write its own default constructor, compiler won't generate one for him and initialization can be problematic even if he use value initialization.
```cpp
struct Widget {
	Widget() {}
	int i;
	std::string s;
	int* pi;
};

int main() {
	Widget w{}; // Value initialization - only string is initialized.
}
```

`default` keyword lets the compiler generate the default constructor.
```cpp
struct Widget {
	Widget() = default;
	int i;
	std::string s;
	int* pi;
};

int main() {
	Widget w{}; // Value initialization - all initialized as 0,'',nullptr
}
```

- As a guideline, programmer should avoid writing empty default constructor. Prefer to let the compiler provide a definition or define by `=default`.
- Assigning and initialization is different and programmer should care about it. Programmer should use constructor initialization list instead of assigning in the constructor body. Assignments are accepted as changing the state of the object.
**Assignment in constructor body**
```cpp
struct Widget {
	Widget() {
		i = 42;           // Assignment, not initialization
		s = "emretasar";  // Assignment, not initialization
		p = nullptr;      // Assignment, not initialization
	}
	int i;
	std::string s;
	int* p;
};

int main() {
	Widget w{}; // Value initialization - all initialized as 0,'',nullptr
}
```
**Initialization**
Programmer should define and initialize member variables in the order of member declaration. That is not optional, that is the binding order and programmer have to initialize data members exactly in that order in the member initializer list.
```cpp
struct Widget {
	Widget() 
	:   i {42},           // Initialization
		s {"emretasar"},  // Initialization
		p {nullptr}       // Initialization 
	{
	}
	int i;
	std::string s;
	int* p;
};

int main() {
	Widget w{}; // Value initialization - all initialized as 0,'',nullptr
}
```

### 2- The Destructor
- Destructors are used to clean up the object in destruction. 
- The compiler generates the destructor if the destructor is not explicitly declared.
- The compiler generated destructor calls the destructor of all data members of class (user-defined) types. But it does not do anything special for fundamental types.
```cpp
class Widget {
	public:
	~Widget() {       // We write our own destructor because
		delete pr;    // compiler generated one does not destroy fundamental types.
	}                 // If this class own the pr and manages its lifetime, 
					  // we should also clean up it manually. 
					  // If we don't it is a resource leak.
	private:
	int i;
	std::string s;
	Resource* pr;
};
```

- Never provide an empty destructor. Prefer to let the compiler provide a definition or define by `=default`.
- Provide a manual destructor if the class has any owning pointers.
- Static members live for the duration of the program not for the duration of a single object. So destructors does not concern about static members at all.

### 3- The Copy Constructor and Copy Assignment Operator
```cpp
// Copy Constructor
	Widget(Widget const&);  // Default Signature - Stick to it 99%
	Widget(Widget&);        // Possible but not reasonable
	Widget(Widget);         // Not Possible - recursive call

// Copy Assignment Operator
	Widget& operator=(Widget const&); // Default - Stick to it 99%
	Widget& operator=(Widget&);       // Possible but not reasonable
	Widget& operator=(Widget);        // Reasonable; builds on the copy constructor
```

- The compiler always generates the copy operations 
	- if they are not explicitly declared and
	- if no move operation is declared and
	- if all bases and data members can be copy constructed/assigned 
- If you have move operation, compiler will implicitly delete the copy operations. If you have move operation in the class and you try to copy an object, you will get a compilation error.
- Every class has a copy constructor and copy assignment operator. Either they are available or deleted. `delete` keyword does not discard the method, it disables it to be called.
#### 3.1- The Default Implementation
```cpp
class Widget
{
public:
Widget(Widget const& other)    // The default copy constructor performs
	: Base{other},             // member wise copy construction of all data members
	i {other.i},
	s {other.s},
	pr {other.pr}    // Shallow Copy - it might result with double delete
{}
Widget& operator=(Widget const& other)   
{                               // The default copy assignment operator
	Base::operator=(other);     // performs a member wise copy assignment
	i = other.i;                // of all data members
	s = other.s;
	pr = other.pr;   // Shallow Copy - it might result with double delete
	return *this;
}
~Widget() { delete pr; }

private:
int i;
std::string s;
Resource* pr{};
};
```
- This implementation might not be a good idea if you have pointer member variables. Because if class has owning pointer of some resource like in the example, programmer should write own destructor. But if you copy the object by copy constructor or copy assignment operator, both objects have started to think they own the same pointer and they try to delete same pointer. This causes the double delete problem.   
- Also default implementation does not work if you have const member variables because const variables cannot be copied. Programmers should try to avoid to have const member variables data. const members and reference member variables are troublesome because of they mess up things with copying and moving.
#### 3.2- We Can Come Up With a Implementation Like Below
```cpp
class Widget
{
public:
Widget(Widget const& other)    
	: Base{other},            
	i {other.i},
	s {other.s},
	pr {other.pr ? new Resource{*other.pr} : nullptr}    
{}
Widget& operator=(Widget const& other)   
{   
	if (this != &other)
		delete pr;                           
	Base::operator=(other);     
	i = other.i;                
	s = other.s;
	pr = other.pr ? new Resource{*other.pr} : nullptr;   
	return *this;
}
~Widget() { delete pr; }

private:
int i;
std::string s;
Resource* pr{};
};
```
- In this implementation we do not shallow copy pointers and we started to clean up the previous resource pointer. 
- But with this implementation we started to do everything with ourselves. Just a single pointer got us into much trouble.
#### 3.3- Simpler Implementation - Swap Idiom
- Not fastest solution but simpler
- You should write your swap function.
```cpp
class Widget
{
public:
Widget(Widget const& other)    
	: Base{other},            
	i {other.i},
	s {other.s},
	pr {other.pr ? new Resource{*other.pr} : nullptr}    
{}
Widget& operator=(Widget const& other)   
{   
	Widget temp(other);
	swap(tmp);
	
	return *this;
}
~Widget() { delete pr; }

private:
int i;
std::string s;
Resource* pr{};
};
```
#### 3.4- Faster Implementation
- - You should write your swap function again.
```cpp
class Widget
{
public:
Widget(Widget const& other)    
	: Base{other},            
	i {other.i},
	s {other.s},
	pr {other.pr ? new Resource{*other.pr} : nullptr}    
{}
Widget& operator=(Widget const& other)   
{   
	if (pr && other.pr) {
		Base::operator=(other);     
		i = other.i;                
		s = other.s;
		*pr = *other.pr; 
	} else {
		Widget tmp(other);
		sway(tmp);
	}	                           
  
	return *this;
}
~Widget() { delete pr; }

private:
int i;
std::string s;
Resource* pr{};
};
```
#### 3.5- Using Smart Pointers
- Until know we try to solve the problems that is resulted from using a raw pointer. We have raw pointer that we own, so we needed to implement our own destructor. By implementing our own destructor, we needed to implement our own copy constructor and copy assignment operator because default implementation has copying shallowly. We had to apply Rule of Three. It gave us so much trouble.
- Whatever we prefer to use unique pointer? We do not need to implement our own destructor because smart pointers will handle it themselves. But still we need to have copy constructor and copy assignment operator because unique pointers are not copyable. 
- So we can say we should using shared pointer. But it is not that easy because our object had its own resources when we were using raw or unique pointers. If we decided to use shared pointer, our object started to share resources. And it is really a big decision that we can not easily decide. But if there is no problem in there with ownership and we can use shared pointer, our world becomes so much easier. We do not need to write our own destructor, copy constructor and copy assignment operator. What a relief! This is called as Rule of Zero which says classes that don't require an explicit destructor, copy constructor and copy assignment operator are much easier to handle. 

### 4- The Move Constructor and Move Assignment Operator
```cpp
// Move Constructor
	Widget(Widget&&); noexcept     // Default Signature - Stick to it 99%
	Widget(Widget const&&); noexcept // Possible but uncommon


// Move Assignment Operator
	Widget& operator=(Widget&&);       // Default - Stick to it 99%
	Widget& operator=(Widget const&&); // Possible but uncommon
```

- The compiler generates the move operations
	- if they are not explicitly declared and
	- if no destructor and no copy operation is declared and
	- if all bases/data members can be copy or move constructed/assigned. If there is  a member which not copyable and not moveable at the same time, the compiler won't generate move constructor and move assignment operator.

#### 4.1- The Default Implementation
```cpp
class Widget
{
public:
Widget(Widget&& other) noexcept // The default move constructor performs
	: Base{std::move(other)},   // member wise move construction of all data members
	i {std::move(other.i)},
	s {std::move(other.s)},
	pr {std::move(other.pr)}    // Shallow Copy - it might result with double delete
{}
Widget& operator=(Widget&& other) noexcept   
{                                       // The default move assignment operator
	Base::operator=(std::move(other));  // performs a member wise move assignment
	i = std::move(other.i);             // of all data members
	s = std::move(other.s);
	pr = std::move(other.pr);   // Shallow Copy - it might result with double delete
	return *this;
}
~Widget() { delete pr; }

private:
int i;
std::string s;
Resource* pr{};
};
```

- This implementation will have the same problems that are discussed in the copy constructor and copy assignment operator section. So we will need to implement our own move assignment operator and move constructor again. This will lead us to Rule of Five which says when you require a destructor, you most probably also require the two copy operations and two move operations. 
- When we use unique pointer instead of raw pointer, we get rid of the destructor, move constructor and move assignment operator because unique pointers handle move operations. But we still need to write our own copy operations. 
- Again if using shared pointer works in our case, we also get rid of the copy operations but still we need to keep in mind this is a radical change in class. 
## Rule of 0-3-5-6

|               | Default Constructor | Copy Constructor | Copy Assignment Operator | Move Constructor | Move Assignment Operator | Destructor |
| :-----------: | :-----------------: | :--------------: | :----------------------: | :--------------: | :----------------------: | :--------: |
| Rule Of Zero  |          X          |        X         |            X             |        X         |            X             |     X      |
| Rule Of Three |          X          |        ✓         |            ✓             |        X         |            X             |     ✓      |
| Rule Of Five  |          X          |        ✓         |            ✓             |        ✓         |            ✓             |     ✓      |

- Rule of Zero says that you don't have to implement none of them and compiler will generate them for you. This is a programmers goal. If programmer does not need to implement none of them and be able to use compiler generated ones, it is the best option.
- Rule of Three says that if you require a destructor, you most probably also require a copy constructor and copy assignment operator.
- Rule of Five says that if you require a destructor, you most probably also require a copy constructor, copy assignment operator, move constructor and move assignment operator.
## Summary
- If you can avoid defining default operations, do
- If you define or  `=delete` any default operation, define or `=delete` them all.
- Follow the Rule of Five if you want to default/delete the move operations.
- Follow the Rule of Three if you want to copy instead of move operations.
- Try to reduce the use of pointers
- Prefer `unique_ptr` over `shared_ptr` unless you need to share ownership
- Be suspicious of manual resource cleanup (RAII)
